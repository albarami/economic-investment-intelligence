# Offline activity review triage

S2-T05 implements PUB-35 and AI-98. Run from the repository root:

```sh
uv run --locked python scripts/spine_triage.py --queue data/public_cache/queue.csv --cache data/public_cache --review custodian/publicdata/review/activity_spine.csv --membership data/public_cache/membership.json --run-id local-review
uv run --locked python -m unittest scripts.tests.test_spine_triage -v
```

`EII_DECISION_PROVIDER` defaults to `none`. No connection, key or configured
adapter is needed. The queue must exactly equal the S2-T04 recomputed queue,
including baseline order, reasons and empty sign-off fields. Membership JSON
has exactly `playbook_codes`, `supplier_codes` (lists using S2-T04's reversible
code encoding), and `supplier_complete` (true). Inputs stay within the repository;
the cache stays under `data/public_cache`. Symlinks and output reuse refuse.
Receipts and classification titles are checked by S2-T04; no source is fetched.

`recorded` additionally needs `--fixtures` pointing to the gateway's handwritten
replay JSON contract. These tests demonstrate mechanics, never qualification.
Eligible seven-digit codes with valid class prefixes get fixed yes/no requests;
legacy and invalid-prefix codes receive no request. Confident mismatches come
first, unresolved and ineligible rows next, confident matches last, preserving
baseline order within each group. Nothing is removed or approved.

Outputs are local, uncommitted files under
`data/public_cache/spine_triage/<run-id>/`:

- `queue.csv`: unchanged S2-T04 columns and row values, optionally reordered.
- `suggestions.csv`: `code,candidate_isic_class,suggestion,memo_key`; labels are
  `match`, `mismatch`, `unresolved`, `ineligible`. Ineligible rows have empty
  candidate and evidence fields. This file is not a review file.
- `queue.binding.json`: the existing ReviewedBinding format recording title
  identities and code-system version; it is not a signature.
- `manifest.json`: input and receipt hashes, source attribution, output hashes,
  method/rubric/route identity and run accounting, with no payload or scores.

Gateway records retain DAT-126 and null `human_disposition` and are written only
under `evals/typed_decisions/runs/`. A person reviews each meaning, transfers that
row into the S2-T04 review CSV, records their reviewer role and date and carries
the matching binding. Previously signed rows must be preserved. Rebuild and
finalise through S2-T04. Unsigned legacy acknowledgements also require individual
review; copying the queue or suggestions into the review path cannot complete it.

## Lead-only keyed procedure

Workers, tests and CI never select a keyed provider. Before a lead-shell run,
the lead confirms OI-18's remaining build allowance and selects a positive
`--token-cap` no greater than the per-run limit and remaining allowance.
The lead supplies `--authorised`, `--endpoint` and `--qualification`. The latter
is a local JSON record with exactly `qualified: true`, `model`, `rubric_id`,
`rubric_sha256`, `language` and `route`. These must match the constants of
`spine_triage.py`; route is its route constant followed by a hyphen and the
endpoint SHA-256. Qualification must be human-confirmed for that exact identity
(decision 0014, “What would change this decision”). An aggregate qualification
for another rubric is refused. No qualifying evidence is generated by triage.
The gateway alone reads the key from the environment when the lead runs it.
Never place endpoint or key values in a committed report. The lead records
sanitised token totals in PROGRESS, and checks remaining allowance before use.

Exit 0 means an unsigned queue was written. Exit 3 means input or authorisation
refusal, with a fixed diagnostic. Exit 4 means keyed failure: no follow-on call
or retry, the complete baseline queue and unresolved suggestions are written.
There is no application import, table, screen or automatic mapping.
